# Rent A100 80GB by the Hour: Planning a Glows.ai Workload

To rent A100 SXM4 80GB by the hour, start with the exact configuration and billing terms, then budget for the workload’s complete billable duration. Glows.ai’s November 2026 public on-demand reference is $1.20 USD equivalent per listed instance-hour for A100 SXM4 80GB, with per-second compute billing.

Pricing on November 2026: [official GPU pricing](https://glows.ai/zh-TW/gpu-pricing). Rates are credits/hour for the listed configurations. Dollar amounts below are USD equivalents using the confirmed 1 credit = US$1 conversion; confirm booking terms.

That rate is a useful starting point for a fine-tuning or self-hosted inference pilot. It does not establish a node quote, a managed endpoint price or a guaranteed runtime. The next step is to define the job the instance must complete and measure it under conditions you can repeat.

## Confirm what “A100 SXM4 80GB” means in the offer

Keep the memory specification in the quote. An A100 40GB listing is not the same configuration as A100 SXM4 80GB. Also confirm the listed variant, GPU count, included CPU and RAM, storage, network terms and any whole-node requirement.

A per-GPU figure can look affordable while requiring several GPUs to be rented together. Use the actual allocation in the budget. If the offer is priced per node, use that node price directly rather than multiplying it by GPU count again.

Check purchasing terms separately: on-demand, interruptible and committed capacity can have different prices and responsibilities. An aggregator’s older headline is not proof that the same offer remains available today.

For per-second compute billing, convert billable seconds to hours and apply the rate. Include every billable phase once: preparation, loading, execution, idle periods and retries. Keep engineering labor estimates separate from the cloud invoice.

Finishing a script, unloading a model or closing a browser tab does not establish that instance billing has ended. Retain the necessary files and check the resource’s billing state when closing the experiment.

## Decide whether the pilot is training or serving

An 80GB GPU can support a different memory budget from a smaller card, but it is not a universal model-size guarantee. The complete software and workload configuration still determine fit.

For fine-tuning, distinguish full-parameter training from LoRA or QLoRA. Weights, gradients, optimizer state, activations and temporary buffers all matter. The model’s inference footprint does not establish its training requirement.

For inference, include runtime buffers and KV-cache requirements. Long contexts and overlapping requests can change memory demand after a short single-request test has already succeeded.

Write those conditions down before comparing another instance. A lower hourly rate and a larger memory figure answer different questions; neither substitutes for the actual workload test.

## Choose a software starting point

Glows.ai’s image catalog includes PyTorch and LLaMA-Factory environments for training work and vLLM environments for self-managed serving. SSH access gives developers ways to inspect dependencies, files and logs.

Select the image against the actual model, framework and GPU requirements. Pin the code commit, model/tokenizer revisions, Python/CUDA/framework versions and launch settings. Record any additional packages or downloads so a later session can reconstruct them.

A cataloged environment reduces basic assembly, while the pilot establishes compatibility. It is not a claim that every training recipe works unchanged or that a model-specific runtime is a one-click training service.

## For fine-tuning, compare cost at the same quality

Use a representative dataset with a held-out validation split and a task-specific acceptance threshold. Keep sequence length, training method, precision and batch settings in the result record. If you change them, describe why the comparison remains meaningful.

A short pilot can reveal memory and compatibility problems. Extend a viable setup before estimating the final run from early throughput alone. Validation, checkpoint I/O and later training behavior can add work outside the first measured batches.

Save and reload a checkpoint before the long job. Training resumption can require optimizer, scheduler and other state as well as model weights. Include failures and retries when calculating cost to reach the validation target.

Glows.ai Team can organize shared GPUs, environments, datasets, permissions and quotas around the experiment. Keep a run manifest and an owner alongside those resources; shared access does not record every setting automatically.

## For inference, compare cost within service targets

Fix model revision, precision, input/output lengths, concurrency and quality requirements. Measure time to first token where relevant, completion latency, successful throughput and errors. Retain the request count and describe how failed requests are treated in latency statistics.

Separate cold loading from warm operation for diagnosis, then include all applicable billable time in the cost. A continuously allocated model may incur idle compute even while it answers no requests.

Use the total evaluation charge divided by qualifying successful responses to calculate cost per useful result. For token accounting, retain actual input and output totals and the latency target. Public instance rates do not directly define managed endpoint or token prices.

If a managed deployment is preferable, evaluate Glows.ai Inference on Cloud separately and obtain the relevant terms. Its autoscaling does not establish scale-to-zero billing or support for an unchanged self-hosted configuration.

## Keep a quote-and-result record

Save the date, GPU identity, rental size, included resources, billing terms, image and model versions, task settings, output criteria, billable duration and separately charged services. Add artifact locations and confirmed retention terms.

That record makes a second configuration easier to compare and gives a teammate enough information to inspect the decision. Test file retrieval before releasing compute, especially when the experiment produces checkpoints you cannot easily regenerate.
