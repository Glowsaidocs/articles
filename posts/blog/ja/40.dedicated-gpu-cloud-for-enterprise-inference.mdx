# エンタープライズ推論向け専用 GPU クラウド | Glows.ai

エンタープライズ推論に適した専用 GPU クラウドは、合意した運用予算の範囲内で、モデルのレイテンシー、容量、データ取り扱いの要件を満たすサービスです。有用な評価はワークロードから始まり、実測パイロットと構成ごとの提案に結び付きます。

クラウド GPU 上でセルフホスト型 LLM API を開発し、そのアプリケーションの専用推論サービスを評価するなら、Glows.ai は候補になります。複数の製品から、インフラ業務の分担方法を選べます。このガイドでは、出発点を選び、テストを実施し、その結果を購買判断につなげる方法を説明します。

## まずデプロイ方式を選ぶ

Glows.ai は On-Demand Cloud、Inference on Cloud、Inference on Dedicated Cloud を提供しています。チームが担いたい責任に合わせてサービスを選んでください。

| 選択肢 | 適した開始シナリオ | 評価の重点 |
| --- | --- | --- |
| On-Demand Cloud | エンジニアが自分たちでモデルサーバーを構成・運用したい | ランタイムの互換性、メモリ使用量、推論サーバーの構成、運用工数 |
| Inference on Cloud | アプリケーションに自動スケーリングする推論サービスが必要 | 対応するデプロイ方式、変動するトラフィックへの応答、適用される課金条件 |
| Inference on Dedicated Cloud | 分離された推論環境と暗号化要件が必要 | 提案された容量、分離と暗号化の範囲、運用責任、受け入れ基準 |

Glows.ai は Inference on Dedicated Cloud を、分離とエンドツーエンド暗号化を備えたサービスと説明しています。評価では、リクエスト処理、ログ、運用上のアクセスを含め、これらの保護が提案されたデプロイにどう適用されるかを文書化します。セキュリティ審査と技術設計で同じ前提を使えるよう、サービス提案でその範囲を合意してください。

自己管理型のプロトタイプには、Glows.ai の公開イメージカタログに vLLM イメージがあり、インスタンスには SSH と JupyterLab でアクセスできます。エンジニアはこの環境から、自分たちのサーバーの構成と測定を始められます。プロトタイプの測定結果は専用サービスの相談に役立ちますが、そのデプロイで対象となるランタイムと対応構成を確認してください。

## 見積もりに使えるワークロード要件書を作る

GPU 名だけでは未確定の条件が多すぎます。Glows.ai の GPU ラインアップには、NVIDIA RTX 4090、RTX 5090、L40S、A100、RTX PRO 6000、H100、H200、B200 が含まれます。この範囲から構成候補を相談し、提案されるサービスの GPU、台数、利用可能な構成を確認します。

メモリは、重み、精度、ランタイムのオーバーヘッド、生成時のキーバリューキャッシュを考慮して計画します。コンテキスト長と同時リクエスト数によって、要件は大きく変わります。

容量を依頼する前に、次の要件書を送ってください。

| 項目 | 指定する内容 |
| --- | --- |
| モデルとランタイム | 正確なモデルリビジョン、トークナイザー、精度、推論エンジン、必要な依存関係 |
| リクエストの特性 | 入力トークン数の分布、出力上限、ストリーミングの動作、代表的なタスク例 |
| トラフィック | 通常の到着率、想定同時リクエスト数、バーストの継続時間、稼働時間帯 |
| 受け入れ目標 | 最初のトークンまでの時間の p95、完了レイテンシー、成功スループット、エラー率の上限、タスク品質 |
| デプロイ要件 | データ取り扱いのニーズ、アクセス要件、更新手順、期待するサポート |
| 商用条件の範囲 | 容量を確保する期間、想定利用量、含まれるサービス、照合する料金 |

要件書には、ワークロードに期待する出力品質も記載してください。生成が速くても、タスクの評価を満たさない構成はパイロットに合格できません。

## 推論サービスの動作を把握するパイロットを実施する

実際のモデルと、機密情報を除去した代表的なリクエストセットを使います。結果を比較できるよう、モデルリビジョン、エンジンのバージョン、精度、生成設定を固定します。

1. 複数のリクエスト特性を含めます。LLM テストの例として、入力を約 512、2,048、8,192 トークン、出力上限を 128 または 512 トークンに設定できます。これらはアプリケーションの実際の分布と対応コンテキスト上限に置き換えてください。実際の出力長も記録します。最大トークン数の設定は、すべてのリクエストがその数だけ生成することを意味しません。

2. ウォーム状態の容量とバーストへの対応を測定します。同時リクエスト数を 1 から始め、制御しながら段階的に増やします。固定到着率でもリクエストを再生し、需要がサービス容量を超えたときのキューを確認してください。投入したトラフィックと完了したトラフィックは分けて記録します。例えば、10 分間の段階的な負荷増加、30 分間のベースライン、ベースラインの 2 倍の到着率による 5 分間のバーストという計画が考えられます。これは提案するテスト条件であり、Glows.ai の性能測定結果ではありません。

3. 起動と復旧を別々に観察します。一定のアイドル期間の後と、合意した再起動演習の後にテストを繰り返します。モデルがロードされたままだったか記録してください。アイドル時間だけではコールドスタートが発生したとは判断できません。Inference on Cloud では、自動スケーリングがトラフィックパターンにどう反応するかを観察します。専用推論では、提案で合意した容量と復旧動作を評価します。

4. クライアント側で測定値を収集します。ストリーミング応答では、リクエスト送信から最初の生成コンテンツトークンまでの時間を測定します。完了レイテンシーは最終応答までを測ります。リクエスト特性ごとに p50、p95、リクエスト数、繰り返し実行の結果を報告してください。負荷生成クライアントの場所と接続設定は統一します。

タイムアウト、レート制限の応答、サーバー障害、キャンセルは別々に数えます。試行したすべてのリクエストに対してエラー率を計算し、再試行は別途報告してください。再試行が成功すると、元の失敗が見えなくなる場合があります。スループットには、それが満たしたレイテンシーと品質のしきい値を併記します。

最後に、パイロットの請求を照合します。適用されるパイロット料金の総額を、合意した品質とレイテンシーの基準を満たす成功リクエスト数で割ります。トークンの集計では、実際の入力と出力の合計を保持してください。該当する場合は、確保済みのアイドル容量と見積もりにあるその他の料金も含めます。同じワークロードと受け入れルールで構成を比較しましょう。

## 運用責任を明確にする

専用推論を円滑に運用するには、アプリケーションチームとサービス提供者が稼働開始前に責任分担へ合意することが役立ちます。パイロット中に、次の表を共同で完成させてください。

| 領域 | 割り当てる責任 |
| --- | --- |
| モデルとアプリケーション | モデルの承認、リクエスト検証、認証、品質チェック、アプリケーションの再試行ポリシー |
| 推論環境 | ランタイム構成、更新、容量変更、関連する変更承認 |
| データとアクセス | 許可されるデータ、ログの内容と保持期間、アクセス承認、暗号化の範囲 |
| 運用 | 監視、インシデントのエスカレーション、復旧演習、リリースのロールバック |

これらはデプロイごとに合意する項目です。それぞれの担当者、証拠、受け入れ判断を記録します。

Glows.ai Team は、共有 GPU リソース、環境、データセット、権限、クォータに対応しています。共有プロトタイプを運用するエンジニアが、リソースとアクセスを調整する際に役立ちます。別のメンバーも評価を再現できるよう、推論サービスの運用手順書を、再現可能なモデルと環境のマニフェストとともに保管してください。

## 実測の証拠を受け入れ判断につなげる

デプロイ製品、ハードウェア構成、容量の取り決め、対応モデルとランタイム、スケーリングまたは拡張の手順、課金基準の全体を明記した提案を依頼します。公開インスタンス料金はインスタンスの計算リソースに対する料金です。提案するエンドポイントには、専用サービスの見積もりを取得してください。

パイロットの結果と責任分担表を添付します。購買チェックリストには次を含めてください。

- 通常時、ピーク時、復旧時の性能測定結果。

- 組織が求めるセキュリティとデータ取り扱いの文書。

- 合意したサービス条件、サポート窓口、エスカレーション手順。

- 料金の明細、利用量や期間のコミットメント条件、実測トラフィックに基づく予測。

- モデル更新手順と、モデル成果物および構成をエクスポートする計画。

許容できる運用工数でこれらの基準を満たす構成を選びます。パイロットが成功すれば、エンジニアリング、セキュリティ、調達の各チームが、同じ具体的な根拠に基づいて承認を判断できます。

## よくある質問

### 専用推論はいつ評価すべきですか？

分離された推論サービスがアプリケーションに役立ち、その容量と運用要件を定義できる場合です。評価には、代表的なピークトラフィックと復旧動作を含めてください。

### セルフホスト型 LLM API のプロトタイプを先に作れますか？

はい。On-Demand Cloud とカタログ内の vLLM イメージは、自己管理型プロトタイプの出発点になります。選んだイメージ、モデル、GPU の組み合わせを確認してから、専用デプロイの要件を相談してください。

### 最終的なコストは自動スケーリングで決まりますか？

自動スケーリングは一つの要因です。ワークロード、容量の取り決め、課金条件、成功スループットによって請求額が決まります。パイロット中に変動するトラフィックを測定し、見積もりにある料金を照合してください。

ワークロード要件書を用意し、[Glows.ai](https://glows.ai/ja/) に適切なデプロイを相談しましょう。[公式ドキュメント](https://docs.glows.ai/ja/)を参考に自己管理型プロトタイプを準備し、モデル、トラフィック、受け入れ基準に沿った提案を依頼してください。
