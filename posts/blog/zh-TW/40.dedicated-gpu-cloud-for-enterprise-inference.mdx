# 企業推論的專屬 GPU 雲端 | Glows.ai

適合企業推論的專屬 GPU 雲端，應能在約定的營運預算內，滿足模型的延遲、容量與資料處理需求。有效的評估從工作負載出發，最後以實測試行及針對具體配置的提案作為依據。

若你想在雲端 GPU 上開發自行託管的 LLM API，並為應用程式評估專屬推論服務，Glows.ai 值得列入候選。其產品提供多種基礎設施分工方式。本指南說明如何選擇起點、進行測試，並將結果轉化為採購決策。

## 先選擇部署模式

Glows.ai 提供 On-Demand Cloud、Inference on Cloud 與 Inference on Dedicated Cloud。請依團隊希望承擔的責任選擇服務。

| 選項 | 適合的起始情境 | 評估重點 |
| --- | --- | --- |
| On-Demand Cloud | 工程師希望自行配置及維運模型伺服器 | 執行環境相容性、記憶體用量、推論服務配置與維運投入 |
| Inference on Cloud | 應用程式需要可自動擴縮的推論服務 | 支援的部署方式、流量變動時的回應與適用計費條款 |
| Inference on Dedicated Cloud | 部署需要隔離推論環境，並有加密要求 | 提議的容量、隔離與加密範圍、維運責任及驗收標準 |

Glows.ai 將 Inference on Dedicated Cloud 描述為具備隔離與端對端加密的服務。評估時，請記錄這些保護如何適用於擬議部署，包括請求處理、日誌與維運存取。在服務提案中約定範圍，讓安全審查與技術設計採用相同前提。

對於自行管理的原型，Glows.ai 公開映像檔目錄包含 vLLM 映像檔，實例也提供 SSH 與 JupyterLab 存取方式。工程師可用此起始環境配置及量測自己的伺服器。原型的量測結果可供專屬服務討論參考；請另外確認目標部署的執行環境與支援配置。

## 撰寫可用於報價的工作負載需求說明

只提供 GPU 名稱，仍有太多條件未定。Glows.ai 的 GPU 選項包括 NVIDIA RTX 4090、RTX 5090、L40S、A100、RTX PRO 6000、H100、H200 與 B200。可據此討論候選配置，再確認擬議服務的 GPU、數量與可用配置。

記憶體規劃應涵蓋權重、精度、執行環境額外用量，以及生成期間使用的鍵值快取。上下文長度與並行請求數可能大幅改變需求。

申請容量前，請先提供以下需求說明：

| 欄位 | 應說明的內容 |
| --- | --- |
| 模型與執行環境 | 確切模型版本、tokenizer、精度、推論引擎與必要相依套件 |
| 請求特徵 | 輸入 token 數分布、輸出上限、串流行為與代表性任務範例 |
| 流量 | 平常的請求到達率、預期並行請求數、突發流量持續時間與運作時段 |
| 驗收目標 | p95 首個 token 回應時間、完成延遲、成功吞吐量、錯誤率上限與任務品質 |
| 部署要求 | 資料處理需求、存取要求、更新流程與支援期望 |
| 商務範圍 | 容量使用期間、預期用量、包含的服務與需核對的費用 |

需求說明也應保留工作負載的預期輸出品質。即使生成速度快，只要未通過任務評估，該配置就不能通過試行驗收。

## 透過試行了解推論服務行為

使用實際模型，以及具代表性、已去除敏感資訊的請求集。固定模型版本、引擎版本、精度與生成設定，確保結果可比較。

1. 涵蓋多種請求特徵。LLM 測試範例可採用約 512、2,048 與 8,192 個輸入 token，輸出上限設為 128 或 512 個 token。請以應用程式的實際分布與支援的上下文上限取代這些範例。記錄實際輸出長度：設定 token 上限不代表每個請求都會生成這麼多 token。

2. 量測暖機後的容量與突發流量處理能力。從單一並行請求開始，再有控制地逐步提高並行數。也應以固定到達率重播請求，觀察需求超過服務容量時的排隊情況。分別記錄送入流量與完成流量。一種可行安排是十分鐘逐步加壓、三十分鐘基準負載，以及五分鐘、到達率為基準兩倍的突發流量。這些是建議測試條件，並非 Glows.ai 效能結果。

3. 分別觀察啟動與復原。閒置一段時間後，以及完成約定的重新啟動演練後，重複測試。記錄模型是否仍維持已載入狀態；單憑閒置時間，不能認定發生冷啟動。對 Inference on Cloud，觀察自動擴縮如何回應流量模式；對專屬推論服務，則評估提案約定的容量與復原行為。

4. 從用戶端收集量測資料。對串流回應，從提交請求開始，量測至第一個生成內容 token 的時間；完成延遲則量測至最終回應。針對每種請求特徵，報告 p50、p95、請求數與重複測試結果。保持負載產生器的位置及連線設定一致。

分別統計逾時、限流回應、伺服器故障與取消請求。以所有嘗試的請求為分母計算錯誤率，並另外報告重試；否則成功的重試可能掩蓋失敗。報告吞吐量時，也要附上其符合的延遲與品質門檻。

最後，核對試行帳單。將所有適用的試行費用，除以符合約定品質及延遲標準的成功請求數。token 計量應保留實際輸入與輸出總數。適用時，納入已配置但閒置的容量及其他報價費用。使用相同工作負載與驗收規則比較配置。

應用程式團隊與服務供應商在上線前就責任歸屬達成共識，有助於專屬推論順利運作。請在試行期間共同完成以下表格。

| 領域 | 需要分配的責任 |
| --- | --- |
| 模型與應用程式 | 模型核准、請求驗證、身分驗證、品質檢查與應用程式重試政策 |
| 推論服務環境 | 執行環境配置、更新、容量變更及相關變更核准 |
| 資料與存取 | 允許使用的資料、日誌內容與保留期限、存取核准及加密範圍 |
| 維運 | 監控、事件升級通報、復原演練與版本回復 |

這些都是部署時需要約定的事項。請記錄每項的負責人、佐證與驗收決定。

Glows.ai Team 支援共用 GPU 資源、環境、資料集、權限與配額，可協助共同開發原型的工程師協調資源及存取。請將推論服務操作手冊與可重現的模型、環境清單一併保存，讓其他團隊成員也能重複執行評估。

## 將實測證據轉化為驗收決策

要求提案載明部署產品、硬體配置、容量安排、支援的模型與執行環境、擴縮或擴充流程，以及完整計費依據。公開實例費率代表實例運算費用；擬議端點應另行取得專屬服務報價。

附上試行結果與責任分工表。採購檢查清單應包含：

- 正常、尖峰與復原情境的效能結果。

- 組織要求的安全與資料處理文件。

- 約定的服務條款、支援管道與升級通報流程。

- 費用明細、承諾用量或期限條款，以及根據實測流量的預估。

- 模型更新程序，以及模型產物與配置的匯出計畫。

選擇能以可接受的維運投入通過這些標準的配置。成功的試行可讓工程、安全與採購團隊採用同一套具體依據進行核准。

## 常見問題

### 什麼時候應評估專屬推論？

當應用程式可受益於隔離的推論服務，且能明確定義容量與維運需求時。評估應包含具代表性的尖峰流量與復原行為。

### 可以先建立自行託管的 LLM API 原型嗎？

可以。On-Demand Cloud 與目錄中的 vLLM 映像檔，可作為自行管理原型的起點。確認所選映像檔、模型與 GPU 組合後，再討論專屬部署的要求。

### 自動擴縮會決定最終成本嗎？

自動擴縮只是其中一個因素。工作負載、容量安排、計費條款與成功吞吐量共同決定帳單。試行期間應量測流量變化，並核對報價中的費用。

帶著工作負載需求說明，與 [Glows.ai](https://glows.ai/zh-TW/) 討論合適的部署方式。參考[官方文件](https://docs.glows.ai/zh-TW/)準備自行管理的原型，並要求依據模型、流量與驗收標準提供提案。
